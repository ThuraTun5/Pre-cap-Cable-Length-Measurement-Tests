ESP32 board bring-up

After this page you can explain every line of the T01 program, upload it to the Freenove ESP32 board, read what the serial monitor tells you, and say why the board must only be powered from USB for now.

I assumed: you know basic C (variables, if, functions) but not ESP32 details. Goal = understand T01 before you test it.

OverviewMap of this test

T01 has one job: prove that the whole chain works, from your PC to the chip and back, before we connect any other part. The chain has two halves. On the PC you write and build the program. On the board the program runs forever.

Section 1PlatformIO and platformio.ini

Why this matters: every later test is its own small PlatformIO project. If you understand this one file, you understand how all 10 projects are set up.

VS Code is only a text editor. PlatformIO adds the tools: the compiler for the ESP32, the uploader (esptool), and the serial monitor. It reads platformio.ini to know what to do. That is why you must open the folder that contains this file, not the top project folder.

[env:esp32dev]
platform = platformio/espressif32 @ 6.13.0   ; pinned: Arduino-ESP32 core 2.0.17
board = esp32dev
framework = arduino

monitor_speed = 115200       ; must match Serial.begin() in main.cpp
monitor_filters = time       ; prefix each line with a timestamp
upload_speed = 460800        ; safe speed for the board's USB-serial chip
LineWhat it does
[env:esp32dev]Starts one "environment" (one build setup). The name is our choice.
platform = … @ 6.13.0The ESP32 tool package, pinned to one exact version. Without a version, an update can silently change your build.
board = esp32devGeneric definition for ESP32-WROOM-32 modules. Our Freenove board uses the WROOM-32E module, so this fits.
framework = arduinoUse the Arduino functions on top of Espressif's system.
monitor_speed = 115200Serial monitor speed. Must equal Serial.begin(115200) in the code.
monitor_filters = timeAdds the PC time in front of every line you receive.
upload_speed = 460800How fast the firmware is copied. Lower it (e.g. 115200) if uploads fail.

In one sentence: platformio.ini tells PlatformIO which chip, which tools, and which speeds to use.

Small details Text after ; is a comment. The build output goes into a hidden .pio/ folder, which git ignores. The first build downloads several hundred MB of tools and takes minutes. Later builds take seconds (ours: about 12 s).

Section 2The Freenove ESP32 WROOM board

Why this matters: choosing the wrong pin is the most common way to get a board that "does nothing" or will not boot. Every later test uses this map.

The board has 40 pins in two rows of 20. Not every GPIO is equal. Some are power or ground. Some are input-only. Some decide how the chip boots. Two pins already have LEDs on the board.

Pin groupPinsRule for our project
On-board blue LEDGPIO 2Used in T01 to blink. GPIO 2 is also a strapping pin, so we use it only for this LED.
On-board RGB LED (WS2812)GPIO 16Kept as a status light. Not used for anything else.
USB serialGPIO 1 (TX), 3 (RX)Never use. They carry the serial monitor text. The TX/RX LEDs flicker when text moves.
Strapping pinsGPIO 0, 2, 5, 12, 15Avoid for external signals. GPIO 0 is wired to the BOOT button.
Input-onlyGPIO 34, 35, 36 (VP), 39 (VN)Cannot drive anything. Good for reading the encoder later (T4).
Flash pinsGPIO 6–11Used by the memory chip. This board does not even bring them out.

In one sentence: every pin has a job or a limit, so we pick pins from the pin plan, never at random.

Small details A GPIO pin works with 0 V to 3.3 V. More than 3.3 V (for example a 5 V signal) can damage the chip. The two 5V pins and four 3.3V pins are power pins, not signals. The full draft plan is in docs/PIN_PLAN.md.

Section 3Program shape: setup() and loop()

Why this matters: all embedded Arduino programs in this project have this shape, including the final firmware.

A PC program starts, does its work, and ends. A microcontroller program never ends. Arduino splits it into two functions. setup() runs once after power-on or reset. Then loop() runs again, again and again, thousands of times per second.

A few C++ points used in the code:

  • constexpr uint8_t PIN_LED_BLUE = 2; gives a pin number a name. If a pin changes later, you change one line.
  • uint8_t = number 0–255, uint32_t = number 0–4 294 967 295. Both have no sign.
  • F("text") keeps fixed text in flash memory instead of RAM. On ESP32 it makes little difference, but it is a good habit from small Arduinos.
  • Serial.printf("%d", x) prints formatted text, like printf in C.

In one sentence: setup() prepares the hardware once, and loop() keeps asking "is it time to do something?".

Section 4 · the hard ideaNon-blocking timing: millis() instead of delay()

Why this matters: later, the same loop must count encoder pulses, send Wi-Fi data and react to the Stop button. If the loop sleeps in delay(), all of that waits. This idea is the base of the whole final firmware.

The simple way to blink is digitalWrite(HIGH); delay(500); digitalWrite(LOW); delay(500);. It works, but during each delay() the chip does nothing else. A key you type has to wait.

The non-blocking way is like checking a clock instead of sleeping. Each pass, the loop reads the time and asks: has enough time passed since the last toggle? If yes, toggle and remember the time. If no, move on at once.

\[ \text{now} - \text{lastBlinkMs} \;\ge\; T \quad\Rightarrow\quad \text{toggle LED, then } \text{lastBlinkMs} = \text{now} \]

Here now = millis() in ms, lastBlinkMs = time of the last toggle in ms, and T = BLINK_INTERVAL_MS = 500 ms.

Try it: when does the board notice your key?
delay() version notices after—
millis() version notices after< 1 ms

In the delay() version, the key is only checked once per blink cycle, after both delays. So the wait can be up to 2T. In the millis() version, the key is checked in every pass of the loop, so the wait is shorter than 1 ms.

What happens after 49.7 days? Extra

millis() is a 32-bit unsigned number. It counts up to its maximum and then starts again at 0 ("overflow").

\[ 2^{32}\ \text{ms} = 4\,294\,967\,296\ \text{ms} \approx 49.7\ \text{days} \]

The subtraction now - last still gives the right answer after overflow, because unsigned subtraction also "wraps around". This is why we always write now - last >= T and never now >= last + T. The worked example below shows the numbers.

In one sentence: never sleep in the loop. Check the clock, act if it is time, and move on.

Small details setup() still uses delay(500) once. That is fine: it runs only at start, to give the serial monitor time to connect. The Wi-Fi scan in scanWifi() is also blocking (about 3 s), but only when you ask for it with s. The LED pauses during the scan. This is expected.

Section 5Serial monitor and commands

Why this matters: the serial monitor is your window into the chip in every test. Later tests use the same one-letter command idea to start and stop motors.

handleSerialCommand() runs in every loop pass. First it asks Serial.available(): is at least one character waiting? If not, it returns at once (non-blocking again). If yes, it reads one character with Serial.read() and a switch picks the action.

When you press Enter, the monitor also sends invisible characters '\r' and '\n' (carriage return, new line). The code ignores them on purpose. Without that, every command would also print "Unknown command".

\[ t_{\text{send}} = \frac{N \times 10\ \text{bit}}{115\,200\ \text{bit/s}} \]

Each character uses 10 bits on the wire: 8 data bits plus a start bit and a stop bit. Extra

In one sentence: the loop peeks for one character each pass, and a switch turns that letter into an action.

Section 6The RGB LED (WS2812 on GPIO 16)

Why this matters: later we use this LED as a status light (for example green = running, yellow = paused). T01 checks that it works.

A normal LED is on or off. The WS2812 has a tiny controller inside. The ESP32 sends it three numbers on one data wire: red, green, blue, each from 0 to 255. The Arduino-ESP32 core has a ready function for this:

neopixelWrite(PIN_LED_RGB, RGB_LEVEL, 0, 0);   // red at level 20 of 255

We use level 20 of 255, which is about 8 % of full drive per colour. Full brightness is uncomfortable to look at. rgbStep counts 0 → 1 → 2 → 3 → 0 (red, green, blue, off) using % 4 (the remainder after dividing by 4).

Small details — a real bug we hit The first build failed with expected unqualified-id before numeric constant. The constant was first called RGB_BRIGHTNESS. The ESP32 core already has #define RGB_BRIGHTNESS 64. A macro replaces text before compiling, so the compiler saw constexpr uint8_t 64 = 20;, which is nonsense. Renaming it to RGB_LEVEL fixed it.

In one sentence: one function call sets the colour of the on-board RGB LED, using three numbers from 0 to 255.

Section 7Wi-Fi scan and RSSI

Why this matters: in T6 the ESP32 must connect to the Pi's Wi-Fi. A scan now proves the radio and antenna work, and shows how strong signals are in your lab.

WiFi.mode(WIFI_STA) puts the radio in "station" mode, the mode of a normal device that joins a network. WiFi.disconnect() makes sure it does not try to join anything. WiFi.scanNetworks() listens on all channels for about 3 seconds and returns how many networks it heard. For each one we print the name (SSID), the strength (RSSI) and the channel. WiFi.scanDelete() frees the memory afterwards.

RSSI is given in dBm: power on a log scale, relative to 1 milliwatt. The numbers are negative because the received power is much smaller than 1 mW. A number closer to 0 is stronger: −45 dBm is much stronger than −75 dBm.

\[ P\,[\text{mW}] = 10^{\,\text{dBm}/10} \qquad\text{every } 10\ \text{dB} = \text{factor } 10 \]

Quality bands are a common practical guide, not an official standard: better than −50 excellent, −50 to −67 good, −67 to −80 usable, below −80 weak.

In one sentence: the scan proves the radio works, and RSSI tells you how strong each network is (closer to 0 = stronger).

Small details The ESP32 only uses 2.4 GHz Wi-Fi. 5 GHz networks will not appear in the list. That is normal, and it matters later: the Pi's hotspot must use 2.4 GHz.

Section 8The USB power rule

Why this matters: this rule protects your laptop's USB port and the board. It applies from T2 on, when the buck converter starts making its own 5 V.

The board's 5V pins are joined to the USB 5 V line inside the board. Good boards put a diode in between. A diode lets current flow only one way. Freenove does not publish this board's schematic, so we cannot check if it has the diode.

Our rule: during tests, the ESP32 gets power from USB only. Other parts (encoder, level shifter) may use the buck converter's 5 V, as long as all grounds are joined and the buck's 5 V does not go to the ESP32's 5V pin. We decide the final power design at Assembly.

In one sentence: never connect USB and an external 5 V to the board at the same time until we know it is protected.

PracticeWorked example: read the numbers from the code

Problem. Use the T01 code to answer: (a) the blink frequency of the blue LED, (b) how long one full RGB colour cycle takes, (c) how long it takes to send the line CPU cores : 2 @ 240 MHz at 115200 baud, (d) whether blinking still works after millis() overflows, using last = 4 294 967 000 ms and now = 204 ms.

a

Why: the LED toggles once per interval, but one blink needs two toggles (on, then off).

\( T_{\text{period}} = 2 \times 500\ \text{ms} = 1000\ \text{ms} = 1\ \text{s} \quad\Rightarrow\quad f = \dfrac{1}{1\ \text{s}} = 1\ \text{Hz} \)

b

Why: rgbStep has 4 states (red, green, blue, off) and changes every 1000 ms.

\( T_{\text{RGB}} = 4 \times 1000\ \text{ms} = 4\ \text{s} \)

c

Why: count characters, add the line ending, then use 10 bits per character.

The text has 28 characters (spaces count too). The printf format ends with \n = 1 more, so N = 29.

\( t = \dfrac{29 \times 10\ \text{bit}}{115\,200\ \text{bit/s}} = 2.52 \times 10^{-3}\ \text{s} \approx 2.5\ \text{ms} \)

d

Why: unsigned 32-bit subtraction works "modulo \(2^{32}\)", so it wraps around the same way the counter does.

\( (204 - 4\,294\,967\,000) \bmod 2^{32} = 204 + (4\,294\,967\,296 - 4\,294\,967\,000) = 204 + 296 = 500\ \text{ms} \)

500 ≥ 500, so the LED toggles exactly on time. Blinking keeps working.

Sanity check. (a) 1 Hz matches "on/off every 0.5 s" in the test instructions. (b) 4 s matches "red, green, blue, off, once per second". (c) A few ms for one line is far below what the eye notices, so printing does not slow the program. (d) The true time between the two readings is 296 ms (to the wrap) + 204 ms (after it) = 500 ms. Same answer.

Hands-onCode to read and change

This is the heart of main.cpp. The full file is in tests/T01_board/src/main.cpp. It compiled with PlatformIO: SUCCESS, RAM 13.4 %, flash 56.3 %, no warnings.

void loop() {
  uint32_t now = millis();                       // time since start, in ms

  // Blue LED: act only when 500 ms have passed (non-blocking)
  if (blinkEnabled && now - lastBlinkMs >= BLINK_INTERVAL_MS) {
    lastBlinkMs = now;                           // remember when we acted
    blueLedOn = !blueLedOn;                      // flip true <-> false
    digitalWrite(PIN_LED_BLUE, blueLedOn ? HIGH : LOW);
  }

  // RGB LED: next colour every 1000 ms
  if (rgbEnabled && now - lastRgbMs >= RGB_INTERVAL_MS) {
    lastRgbMs = now;
    setRgb(rgbStep);                             // 0 red, 1 green, 2 blue, 3 off
    rgbStep = (rgbStep + 1) % 4;                 // count 0,1,2,3,0,...
  }

  handleSerialCommand();                         // returns at once if no key
}

Small exercise (optional, after the test passes)

Make the blue LED blink at 4 Hz. Which value must BLINK_INTERVAL_MS have? Answer: period = 1/4 s = 250 ms, and one toggle is half a period, so 125. Change the line, upload again, and check that the RGB colours still change once per second. They do, because the two timers do not depend on each other.

Watch outTest traps

  • Charge-only USB cable. The ON LED lights, but no COM port appears. Fix: use a data cable. Check: Device Manager shows no new port.
  • Wrong folder opened in VS Code. PlatformIO shows no Build button or says "not a PlatformIO project". Open tests/T01_board itself, where platformio.ini is.
  • Serial monitor still open during upload. Upload fails with "could not open port" or "access denied". Only one program can use a COM port at a time.
  • Baud mismatch. Random symbols like ⸮⸮ appear. Both monitor_speed and Serial.begin() must say 115200.
  • "Failed to connect … waiting for packet header". Hold BOOT while it shows Connecting.....
  • Name clash with a macro. A strange error at a line that looks correct, such as expected unqualified-id before numeric constant. Rename your constant.
  • Thinking −80 dBm is stronger than −45 dBm. Closer to zero = stronger. 35 dB weaker is about 3000 times less power.
  • Using delay() in the loop. Commands react late or seem "ignored". Use the millis() pattern.
  • Using a strapping pin for a signal. The board sometimes does not boot, or boots into download mode. Check the pin plan first.
  • USB plus external 5 V on the 5V pin. Can back-feed the PC. Not allowed until we verify the board.
