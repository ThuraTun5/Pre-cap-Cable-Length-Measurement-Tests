Encoder counting

After this page you can explain how two square waves tell both distance and direction, why one turn is 8192 counts, why the ESP32 counts in hardware, and how the index pulse proves that no counts are lost.

Section 1 · the hard ideaTwo signals give distance and direction

Why this matters: the slider is pushed both ways by hand. One signal alone could count pulses, but it couldn't tell forward from backward.

Inside the encoder, a pattern on a disc produces two square waves, A and B. They have the same shape, but B is shifted by a quarter period. Look at which signal changes first:

  • A changes before B → turning one way (count goes up).
  • B changes before A → turning the other way (count goes down).

The encoder datasheet says: "A leads B for CCW rotation (viewed from front)". Which way is "+" for our slider we decide in T5.

In one sentence: A and B are the same wave shifted by a quarter, and which one changes first tells the direction.

Section 2Why one turn is 8192 counts

The DIP switches are all OFF, so the encoder gives 2048 pulses per turn on A (and 2048 on B). Each pulse has a rising and a falling edge, on both A and B. That's 4 edges per pulse, and we count every one ("full quadrature"):

\[ \text{counts per turn} = 2048 \times 4 = 8192 \qquad \text{one count} = \frac{360^\circ}{8192} = 0.044^\circ \]

In the program, the angle is simply:

\[ \theta = \text{count} \times \frac{360^\circ}{8192} \]

In one sentence: counting all four edges gives 4 × 2048 = 8192 counts per turn, which is 0.044° per count.

Small details The encoder datasheet lists all resolutions "pre-quadrature", so the final count is always PPR × 4. In T5 we turn counts into mm: the 20-tooth pulley moves 40 mm per turn, so one count ≈ 0.0049 mm. Preview of T5

Section 3Why the ESP32 counts in hardware

Why this matters: if counts are lost, the measured cable length is wrong, and nobody notices.

A fast hand moves the slider at about 0.5 m/s. That is 12.5 turns per second, or about 100 000 counts per second. If the program had to run code for every edge (an "interrupt" per edge), the CPU would be busy most of the time. When Wi-Fi also needs the CPU, edges would be missed.

The ESP32 has a pulse counter (PCNT): a small piece of hardware that watches A and B and counts up or down by itself. The CPU just reads the result whenever it wants. Our code sets it up with the ESP32Encoder library:

ESP32Encoder::useInternalWeakPullResistors = puType::none;  // the 74LVC245 drives the lines
encoder.attachFullQuad(PIN_ENC_A, PIN_ENC_B);   // count all 4 edges: 8192 per turn
encoder.setFilter(PCNT_FILTER);                 // ignore pulses shorter than 1.25 us
encoder.clearCount();                           // start at 0

Section 4The glitch filter

Electrical noise (for example from the motors later) can make a tiny spike on a wire. The PCNT can ignore pulses shorter than a set time, counted in ticks of its 80 MHz clock:

\[ t_{filter} = \frac{100\ \text{ticks}}{80\ \text{MHz}} = 1.25\ \mu\text{s} \]

Real edges at 0.5 m/s are about 10 µs apart, so they easily pass. A noise spike of a few nanoseconds is thrown away. The filter must stay well below the real edge spacing: at the maximum value of 1023 ticks (12.8 µs) it would already eat real counts at 0.5 m/s.

In one sentence: the filter removes spikes shorter than 1.25 µs, while real edges are about 10 µs apart.

Section 5The 16-bit counter and overflow

The hardware counter is only 16 bits: it can count from −32768 to +32767. That's only 4 turns (32767 ÷ 8192 ≈ 4). Our slider needs about 25 turns for 1000 mm.

The library solves this: each time the hardware counter reaches ±32767, a short interrupt adds 32767 to a big 64-bit variable and sets the hardware back to 0. getCount() returns big variable + hardware counter. For us it is just one big number that never overflows.

In one sentence: the small hardware counter is extended in software, so getCount() works for any distance.

Section 6The index pulse proves no counts are lost

Why this matters: it is our built-in quality check for the whole chain: encoder, wires, chip and counter.

The X signal gives one short pulse per turn, always at the same angle. The program uses an interrupt on GPIO32: at the exact moment of the index, it stores the current count. In loop() it compares this with the count at the previous index:

\[ \Delta = \text{count}_{\text{index now}} - \text{count}_{\text{index before}} \;=\; \pm 8192 \quad\text{(one full turn)} \]

If even one edge was lost or doubled, Δ is not 8192 and the program prints CHECK: not one full turn. Turn fast for many turns: if every index still says 8192, the counting is perfect.

void ARDUINO_ISR_ATTR onIndex() {       // runs at the index pulse
  indexCount   = encoder.getCount();    // remember the count at this exact moment
  indexPending = true;                  // loop() prints it (no printing inside an interrupt)
}

In one sentence: the count between two index pulses must be exactly 8192, so the index is a free self-test.

Small details If you reverse direction right at the index, Δ can be a few counts different. That's why the program accepts ±4 counts, and why "same spot again" can appear. The encoder datasheet warns that a stepper motor's magnet can disturb the index. If you test on a motor shaft and A/B counting works but index lines look odd, that may be the cause.

Section 7Why the program prints at most 10 times per second

You wanted the screen to update only when the value changes. But turning by hand changes the count thousands of times per second, and printing every change would flood the serial link (and the screen). So the program checks every 100 ms: if the count changed, it prints one line. Still turning → about 10 lines per second. Not turning → nothing. The counting itself is not slowed down: the hardware keeps counting.

In one sentence: the counter is always exact; only the printing is limited to 10 lines per second.

PracticeWorked example: read the numbers

Problem. After z (zero), you turn the shaft 3 full turns and then a quarter turn more, all in the "+" direction. (a) What count do you expect? (b) What angle does the program print? (c) Has the 16-bit hardware counter overflowed? (d) What would Δ at the next index be?

a

Why: one turn = 8192 counts, a quarter turn = 8192 / 4.

\( 3 \times 8192 + 2048 = 26\,624 \) counts

b

Why: angle = count × 360° / 8192.

\( 26\,624 \times \dfrac{360^\circ}{8192} = 1170^\circ \) (= 3 × 360° + 90°). Turns = 3.250.

c

Why: compare with the 16-bit limit.

26 624 < 32 767 → not yet. One more turn (34 816) would pass the limit, and the library would quietly carry it over.

d

Why: between two index pulses there is exactly one turn.

Δ = +8192 → OK (one full turn).

Sanity check. Units: counts × degrees/count = degrees ✓. 1170° is a bit more than 3 × 360°, which matches "3¼ turns" ✓.

Watch outTest traps

  • Encoder 5V and G swapped. Can destroy the encoder. Read the labels on the housing.
  • An encoder signal wired straight to the ESP32. 5 V on an ESP32 pin. Only 5V and G go to the ESP32 directly.
  • Count only jitters ±1. One of A/B is missing: with a single signal the counter just goes up and down by one.
  • Count goes the "wrong" way. Not a fault: A and B order sets the sign. We choose the sign for the slider in T5.
  • Using a 20 ms debounce like in T3. That would throw away real encoder edges. Encoders need the µs hardware filter, not a ms debounce.
  • Filter set to the maximum (1023). 12.8 µs is longer than the real edge spacing at a fast hand speed: you would lose counts.
  • Index lines missing on a stepper motor shaft. Can be the motor magnet (datasheet note), not your wiring, if A/B work.
  • Printing inside the interrupt. Never do that. The interrupt only stores the count; loop() prints.
