USB link to the Pi

After this page you can read the ESP32's data lines, explain the four message types, and know the one trap your teammate must avoid on the Pi.

Short page. Full details for the Pi programmer are in docs/PROTOCOL.md.

OverviewOne cable, two jobs

Section 1JSON Lines: one message per line

Each message is one line of text in JSON format, ending with a new line. JSON is a standard way to write named values, like "len_mm":430.00. Every programming language can read it, so your teammate's Python code needs only json.loads(line).

Why not normal text like "travel 40 mm"? A program would have to guess where the number is. With JSON, each value has a name.

In one sentence: one line = one message = one JSON object with named values.

zeroed is false after every start-up until someone sends z at the end stop. The Pi should not store lengths while it is false.

Section 3Lost lines and a dead link

seq counts every message: 1, 2, 3 … If the Pi sees 41 then 43, one line was lost. The test tool counts these ("lost lines").

Heartbeat: even when nothing moves, a line arrives every second. If the Pi gets nothing for 2 seconds, the cable or the ESP32 has a problem.

Time: t_ms is the ESP32's own clock since start-up. For the database, the Pi uses its own clock when a line arrives.

In one sentence: seq finds lost lines, the heartbeat finds a dead link, and the Pi's clock gives the real time.

Section 4 · the trapOpening the port can restart the ESP32

Why this matters: a restart loses the zero, so every length after it would be wrong.

The board restarts itself when two USB signal lines (DTR and RTS) change. That's how uploading works. A Pi program that opens the port with default settings can trigger it. The fix is two lines before opening:

ser.dtr = False
ser.rts = False
ser.open()

If it restarts anyway, the ESP32 sends hello with zeroed: false, so the Pi can warn the operator to zero again.
